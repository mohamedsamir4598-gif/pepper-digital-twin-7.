# Pepper Digital Twin Platform (v2)

Decision-support platform for drip-irrigated, fertigated pepper in pots/lysimeters, a greenhouse or a field.
It receives readings (manual, CSV or live sensors), keeps a digital twin of each scale/plot in sync,
**simulates, predicts, optimises and recommends** irrigation and fertigation, and compares twin-managed
against traditional management.

It **recommends only**. It never opens a valve. Approved decisions can be read by a separate,
human-reviewed gateway through the API.

## Run

    pip install -r requirements.txt
    streamlit run app.py                                   # the platform
    TWIN_API_KEY=long-random-secret uvicorn pepper_twin.api:app --port 8000   # sensor API (optional)
    python -m unittest discover -s tests                   # tests (no pytest needed)
    python tests/smoke_app.py                              # headless UI smoke test

Quick start: sidebar -> *Virtual demo (synthetic)* -> tab 1 -> **Generate virtual experiment**, then walk tabs 2-6.
`examples/` holds the same virtual data as CSV so you can see the exact import format.

## Data modes (sidebar)
| Mode | What you do |
|---|---|
| Manual entry | type daily readings per unit into the table (tab 1) |
| CSV import | upload observations / weather / yields (templates provided) |
| Live sensors (API) | sensors or a gateway POST to `/api/v1/observations` with `X-API-Key` |
| Virtual demo | generates the planned 4x4x3 factorial with sensor noise (source = `synthetic`) |

Every row keeps its `source`; the whole analysis runs on the source you pick. Synthetic data are model output,
never measurements. All modes feed the same table, so switching later from manual to sensors changes nothing else.

Conventions: day 1 = first day after transplanting; weight = morning scale reading **before** irrigation;
irrigation/drainage = totals for the whole scale (all pots on it); concentrations in mg/L, EC in dS/m.

## What is inside (`pepper_twin/`)
| Module | Role |
|---|---|
| `models.py` | vectorised pot water + nutrient + salt balance, stage-weighted yield, scale<->storage maths |
| `engine.py` | scalar-Kalman assimilation, adaptive Kc, receding-horizon recommendations, season optimiser (differential evolution), yield-water frontier, closed-loop in-silico trial |
| `calibration.py` | sequential calibration (water -> nutrients -> yield) and leave-one-replicate-out validation against quadratic-surface and mean baselines |
| `compare.py` | paired statistics, factorial RCBD ANOVA, Monte-Carlo virtual trial |
| `scenarios.py` | import DSSAT / HYDRUS / AquaCrop scenario results, benchmark the twin, train surrogates |
| `store.py`, `api.py` | SQLite storage with quality control, sensor REST API |
| `synthetic.py` | weather generator and the virtual experiment |

## Experimental layout it expects
Factor 1 irrigation (4 levels) x factor 2 fertilisation (4 levels) x 3 replicates = 48 units, **one scale per replicate with 3 pots**.
The replicate (scale) is the experimental unit; pots are subsamples. Layout, number of pots, levels and replicates are settings.
For the platform itself: set the number of reference scales (e.g. 3) and use *Average of reference scales* in tab 2.

## Honest limits
* Parameters marked ASSUMPTION in `config.py` are starting values, not validated pepper constants.
* Calibration and cross-validation here were run on **synthetic** data generated by the same model structure:
  that shows the pipeline recovers known parameters, not that the model describes real peppers.
* Salinity and nutrient effects are confounded in a fertilisation factorial; salinity parameters stay fixed assumptions.
* With 3 replicates, parameter uncertainty is large; tab 5 reports the spread across folds.
* The twin-vs-traditional virtual trial depends on the baseline you choose. Use the best fixed combination from your factorial.
* The SQLite file is lost when Streamlit Community Cloud restarts. Set `PEPPER_DB_PATH` to persistent storage or export regularly.
